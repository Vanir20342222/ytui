have the same features. The request was to check every open pull request for
both platforms and add any missing counterpart. Desktop source is
`apps/desktop`; Android is `apps/android` with the shared Rust engine in
`crates/ytui-mobile`.

main `48f611f`, including the follow-up that closes the gaps found on main. Implementing a desktop counterpart is not live, Ghostty or

## Desktop additions on this branch

### Related autoplay and "Recommended" in the queue (parity with #36 and Android `autoplay_related`)

- New setting `autoplay_related` (default on, as on Android), in Settings →
  General ("Autoplay related videos when the queue ends") and
  `examples/config.toml`.
- When the current item is a YouTube video or song and nothing follows it in the
  queue (no later entry, no repeat, no shuffle choice), ytui fetches its related
  list once (`BrowseRequest::Related`). Collections, live streams, the source
  itself and anything already in the queue are excluded; at most 25 are kept.
  Local files and offline/demo mode never fetch.
- Automatic advance and **Next** continue with the first recommendation when the
  queue is exhausted. Only entries that actually play join the persisted queue;
  the recommendation list is memory-only. If the list arrives after a short
  video ended, the first entry still starts. A late duplicate result is ignored.
- The playback queue popup (`p`) is the desktop "Up next": queue entries, then a
  "Recommended" heading and the recommendations. `»` marks what plays next
  (omitted for shuffle and repeat-one, like Android). Enter plays an entry, Del
  removes it. With autoplay off, opening the popup fetches a display-only list
  ("related autoplay is off"), as #36 does.
- Code: `apps/desktop/src/related.rs` (pure helpers and unit tests), App wiring in
  `apps/desktop/src/app.rs`, rendering in `apps/desktop/src/ui.rs`.

### Skippable first-run setup (parity with #34 onboarding)

- Five steps: Welcome, Look & feel (theme with live preview, reduce motion,
  thumbnails), Playback (related autoplay, resume where you left off, local
  positions, SponsorBlock), Your account (connect a browser or cookie file, or
  "maybe later"), and a summary.
- Enter/Tab continue, Backspace/Shift-Tab go back, Esc skips, ↑/↓ choose a row,
  Space/←/→ change it. Choices are drafted and saved through the normal
  settings path when the user finishes or skips, keeping what was chosen (as
  Android does). An unchanged theme restores the previous palette. Space on
  the account step finishes setup and opens the existing account connect flow.
- Shown once per setup version (`setup_version` in the state snapshot; older
  snapshots default to 0), like Android's once-per-version preference. Existing
  users therefore see it once and can skip it. Never shown with `--demo` or
  `--offline`, so screenshots and the PTY fixtures are unaffected. Replay from
  F2 → Settings → "Replay first-run setup" or `:setup`.
- Code: `apps/desktop/src/setup.rs`, `apps/desktop/src/ui/setup.rs`, App
  wiring in `apps/desktop/src/app.rs`. German catalog entries were added for
  all new labels.

## Gaps on main outside the open PRs (fixed in the follow-up)

Found while checking settings on both platforms; the owner then asked for all of
them to be fixed.

### Android: resume where you left off (desktop `resume_on_play`)

- New setting `resume_on_play` (default on, as on desktop) in Settings →
  Playback → Fast playback ("Resume videos where you left off").
- Ordinary video plays from the app (`RustRepository.play`) and Next/automatic
  advance in `PlaybackService.navigate` request the saved position. Music, live
  media, previews and downloads start at 0, and explicit History resume is
  unchanged.
- Automatic resume ignores positions under 5 s (desktop's threshold). Finished
  items already reset their saved position to 0 at the end, as before.
- **Not compiled here.** The Android SDK could not be installed in this
  container (the download was blocked), so there was no Kotlin compile, JVM test,
  lint or emulator run. `javac` found no Java syntax errors in the changed Java
  files (only the expected missing-Android-symbol errors). The Android CI workflow
  on the pull request is the first build.

### Desktop: prefer saved offline copies (Android "Prefer saved offline media")

- New setting `prefer_offline` (default on, as on Android) in Settings →
  Playback. When a completed single-file download of the same video or song
  exists in the same mode (video vs audio; matched by URL or YouTube ID), ytui
  plays the file instead of streaming it.
- The queue, history, resume positions and auto-advance keep the original item.
  A new `PlayerCommand::PlayLocal` gives mpv the local path while the player
  status keeps the YouTube media. SponsorBlock lookup is skipped for saved copies,
  as on Android. Copies with removed SponsorBlock segments, split chapters or
  playlist jobs are not used, because their timeline differs.
- Offline mode can now play and resume online queue/history items that have a
  saved copy; items without one are still refused.

### Desktop: configurable seek step (Android `seek_seconds`)

- `seek_seconds` (1–600, Settings → Playback). The default stays 5 s, the
  existing desktop behaviour; Android's default is 10 s. The shortcut
  descriptions now read "Seek forward"/"Seek back".

### Desktop: video information on catalog rows (Android "Video information")

- `[card_info]` table: `channel`, `views`, `upload_date`, `duration`,
  `section`, `likes`, and `description` (shown in the details panel, since rows
  have no room). Settings → Appearance. Defaults keep the established desktop
  rows: channel, duration, section and description on; views, date and likes
  off. Counts are compact (12K, 1.2M); YouTube's own text is used when available.

### Desktop: preload the next item (Android `preload_next`)

- `preload_next` (default on, as on Android) in Settings → Playback. Once the
  current item has 90 s or less left, ytui asks the player to resolve what plays
  next: the next queue entry, the first entry for repeat-all, or the first
  recommendation. It is sent once per current/next pair.
- New `PlayerCommand::Prepare` fills the player's existing stream cache (the same
  key and 120 s lifetime as Play). A Play that arrives mid-preparation joins the
  in-flight resolution instead of starting another. Preparation is cancelled when
  another item starts, settings change or the account changes. Saved copies,
  local files, live media, yt-dlp mode, offline mode and SOCKS proxies are never
  prepared.
- Draft #17 remains a broader desktop startup project (settled-selection
  preparation, extractor and Node changes). This is the smaller Android-parity
  piece and does not replace it.

### Still platform-specific

Mobile-only by nature: touch gestures, haptics, animation style/speed, the
background-playback toggle and the in-app browser sign-in card. Desktop-only by
nature: mpv/MPRIS, browser-profile import, NetworkManager/VPN, external cliamp
and the clipboard watcher.
